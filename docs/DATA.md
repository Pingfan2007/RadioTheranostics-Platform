# Data model

`data/kg.json` is a compact property graph. It is generated by `tools/build_kg.py` from the
RadioPharm Markdown snapshot; nothing in it is hand-edited.

```jsonc
{
  "meta": {
    "source": "RadioPharm (IDRlab) offline Markdown snapshot",
    "sourceUrl": "https://radiopharm.idrblab.cn",
    "built": "2026-10-23",
    "counts": { "nodes": 4784, "edges": 11258, "byType": {…}, "byRelation": {…} },
    "quality": { … }
  },
  "types": { "drug": { "label": "Drug" }, … },
  "relations": { "TARGETS": "targets", … },
  "nodes": [
    { "i": "drug:RPDGUWPLGA", "t": "drug", "n": "Lutetium Lu-177 vipivotide tetraxetan",
      "d": 7, "p": { "drugType": "Peptide-based RP", "phase": "Approval", "synonyms": [ … ] } }
  ],
  "edges": [
    { "s": 0, "t": 121, "r": "CONTAINS_NUCLIDE" },
    { "s": 0, "t": 44, "r": "INDICATED_FOR",
      "p": { "app": "Treatment", "phase": "Approval", "icd11": "ICD-11: 2E06.0" } }
  ]
}
```

## Node

| Field | Meaning |
| --- | --- |
| `i` | Stable ID: `<type>:<RadioPharm accession>` — e.g. `drug:RPDGUWPLGA`, `target:TA16RTHSLS` |
| `t` | `drug` · `target` · `disease` · `nuclide` · `chelator` · `linker` · `vector` |
| `n` | Display name exactly as in the snapshot |
| `d` | Degree (number of edges) |
| `p` | Type-specific properties, only non-empty values |
| `x` | `1` for *inline* indication nodes (no dedicated snapshot page) |

Type-specific `p` keys:

* **drug** — `drugType`, `phase` (highest reported), `synonyms` (up to 6 short ones)
* **nuclide** — `halfLife`, `radiation`, `decay`, `energy`, `range`, `daughter`, `let`, `source`, `cytotoxicity`
* **target** — `genes`, `uniprot`, `function` (truncated to 420 chars)
* **disease** — `icd11`, `category`
* **chelator / linker / vector** — `formula`, `cid`

## Edge

| Field | Meaning |
| --- | --- |
| `s`, `t` | Node indexes into `nodes` |
| `r` | Relation name |
| `p` | Optional: `app`, `phase`, `icd11` for `INDICATED_FOR` |

Edge direction always reads drug → attribute, even though the UI can traverse it from either
end (the inspector labels reverse traversal with a `←`).

## Build flags

```
--kb PATH        directory of the Markdown snapshot (required)
--out PATH       output file (default data/kg.json)
--enrich         back-fill truncated chelator/linker/vector drug lists over HTTP
--stats-only     print counts, write nothing
```

`--enrich` is needed because five chelator pages in the snapshot cap their "Used in N
radiopharmaceuticals" list at 50 names while declaring up to 403. The builder detects
`declared > listed`, queries
`POST /api/radiopharm/postLinkerChelatorTargetheadDescription` for those pages, and adds the
missing edges. Responses are cached in `tools/.cache/<type>_<id>.json`; a rebuild with the cache
present makes no network calls.

Without `--enrich` the build is fully offline and `meta.quality.componentCoverage` records the
gap.

## Resolution rules

1. Drug → nuclide: exact normalised match on the `nuclide name` field.
2. Drug → target: the `Drug Targets` cell is split on `;`, each name normalised (NFKC, dashes,
   whitespace, brackets) and matched against target page titles.
3. Drug → indication: matched against disease page titles; when no page exists an inline node is
   created with a stable `sha1` suffix, preserving the ICD-11 code and phase on the edge.
4. Drug → chelator / linker / vector: read from the component page's "Used in" list (and the API
   back-fill when `--enrich`).
5. Unmatched references are counted in `meta.quality.unresolved` and never invented.

## Known limitations

* The snapshot's disease folder is a curated subset (135 pages) while drug pages use ~500
  distinct indication strings — hence the inline nodes.
* Component lists in the snapshot are truncated at 50 entries; see `--enrich`.
* Three drug pages lost their ID header and are recovered from `_总目录.csv`.
* The graph only contains entities that participate in at least one relation; two drugs with no
  resolvable relation are therefore absent.
